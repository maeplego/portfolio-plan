# ポートフォリオ全体の書類方針

実装チャットで「要件定義書を書いて」「仕様を固めて」と言われたときの正本。個別 Pxx の中身ではなく、**どの書類を・どこに・いつ・どの粒度で**残すかを決める。矛盾したら本ファイルを `instructions.md` と同じ扱いで優先する。

## なぜ書類を分けるか

コードと `DESIGN.md` だけでは、面接で「なぜその制約があるのか」を再現しにくい。一方で 15 プロジェクトすべてに同じ厚さの文書を先に書くと、実装より先に腐る。

方針は次の 3 点。

1. **実装エージェント向け**と **人間（自分・面接官・レビュア）向け**を分ける
2. **未実装は未実装と書く。** 将来形を現状のように書かない
3. **矛盾したらテストとコードが正。** 次に `DESIGN.md`。`docs/` は追随させる

## 置き場所

| 種類 | 場所 | Git | 読む人 |
| --- | --- | --- | --- |
| 共通方針（本ファイル） | `portfolio-plan/documentation.md` | 入れる | エージェント、自分 |
| 実装チャット用の短い設計 | `portfolio-plan/<project>/DESIGN.md` | 入れる | エージェント必須 |
| 人間向け正式書類 | `portfolio-plan/<project>/docs/` | 入れる | 面接準備、レビュー |
| 製品 README | 各 `pf-*/README.md` | 入れる | クローンした第三者 |
| OpenAPI 機械可読 | 各 `pf-*/packages/openapi` または `deploy/` 横 | 入れる | 実装・連携 |
| チャット記録 | `<project>/chat-context/` | **入れない** | エージェントのみ |

`docs/` は製品リポジトリ（`pf-*`）には置かない。設計の正本はメタ（`project`）に集め、製品側 README から必要ならリンクする。

未着手の Pxx に空の `docs/` は作らない。`DESIGN.md` だけで開始してよい。

## DESIGN.md と docs/ の役割分担

`DESIGN.md` は短く保つ。実装順、スタック、非目標、他 Pxx との契約、デモ観点。エージェントが毎回読む。

`docs/` は厚くてよい。要件のなぜ、外部から見た振る舞い、内部設計の根拠、テスト観点、図。面接で「要件定義と設計を分けて説明して」と言われたときに出す。

同じ事実を二箇所で別の結論にしない。スタック変更は **先に `DESIGN.md`**、そのあと `docs/` を直す。

## 必須セット（各 Pxx がスライスを積み始めたら）

実装が「デモできる塊」になった時点で、次を揃える。P05 の見本は `portfolio-plan/calendar/docs/`。

| ファイル | 日本語名 | 書くこと | 書かないこと |
| --- | --- | --- | --- |
| `docs/README.md` | 索引 | 文書一覧、対象スライス、未実装の明示 | 詳細 |
| `docs/01-requirements.md` | 要件定義書 | 目的、アクター、含む/含まない、機能要件、非機能、受け入れ | クラス名、テーブル DDL |
| `docs/02-specification.md` | 外部仕様書 | ユーザーと API から見た振る舞い、エラー、時刻契約 | 内部モジュール分割 |
| `docs/03-design.md` | 内部設計書 | 構成、データ、競合、セキュリティ、時刻の内部モデル | 「やりたいこと」の再掲だけ |
| `docs/04-test-spec.md` | テスト仕様書 | 観点、ケース、期待結果、自動化の有無 | テストコードのコピペ全文 |
| `docs/05-api.md` | API 仕様書 | パス、入力、出力、ステータス。OpenAPI が無い間の正本 | UI のピクセル |
| `docs/06-diagrams.md` | 図表 | ユースケース、画面遷移、シーケンス、状態、ER | 図だけの重複説明を長々と |

必須の理由: 面接で「要件 / 仕様 / 設計 / テストを分けられるか」を聞かれたときに、ファイル名で答えられるようにする。1 ファイルに全部詰めると、どの層の話か自分でも混ざる。

## 状況によって追加する書類

全部を最初から作らない。必要になったら `docs/` に足し、索引に載せる。

| 書類 | いつ必要か | 置き方 |
| --- | --- | --- |
| 画面遷移図 | Web / モバイル画面がある、または次スライスで作る | `06-diagrams.md`。未実装なら「計画」と書く |
| ユースケース図 | アクターが 2 種類以上、または他 Pxx がアクターになる | 同上。Mermaid のフローでよい（UML ツール必須にしない） |
| シーケンス図 | 同期 API、予約、認可コード、決済など競合や往復がある | 成功系 1 本 + 失敗/競合 1 本を優先 |
| 状態遷移図 | 予約・注文・インシデントなど状態がある | 状態名はコードの enum / CHECK と一致させる |
| ER 図 | テーブルが 3 つ以上 | `schema.sql` と一致。カラム全列は不要 |
| OpenAPI | 他 Pxx が呼ぶ、または P11 ポータルが食う | 製品リポジトリの機械可読ファイルが正。`05-api.md` は要約でもよい |
| 非同期契約 | CloudEvents を出す | `docs/07-events.md` など。overview の JSON 規約に従う |
| インフラ設計 | Compose を超えて K8s / Terraform が本領のとき | P02 は cloud-platform の DESIGN と docs。他 Pxx は `deploy/` の説明で足りることが多い |
| 運用・障害 | SLO、アラート、ランブックが題材のとき（P12 など） | その Pxx の docs |

画面がない API 専用（初期の P05、P07 の学習ジョブなど）でも、**計画中の画面遷移は書いてよい。** 「未実装」を冒頭に書く。

## 書かないもの（意図的）

- 会社のテンプレートを真似ただけの表紙・改訂履歴の儀式（版と日付と対象スライスは各ファイル先頭 1 表で足りる）
- コードを日本語に翻訳しただけの設計書
- 秘密、本番 URL、実在個人
- 未実装を「できる」と書いた受け入れ基準

## 各書類の書き方（共通）

各ファイル先頭に次を置く。

```markdown
| 項目 | 値 |
| --- | --- |
| プロジェクト | Pxx name |
| 対象スライス | 実装済み x–y / 計画 z– |
| 最終更新 | YYYY-MM-DD |
| 矛盾時の正 | 自動テストと製品コード、次に DESIGN.md |
```

本文は日本語。識別子（パス、型、IANA TZ、HTTP コード）はコードと同じ綴り。

図は **Mermaid**（Markdown 内）。PNG の手メンテをしない。ユースケース図は標準 UML が Mermaid で弱いので、アクター → ユースケースのフローで代替してよい。

「なぜこうするか / なぜしないか」を要件か設計のどちらか一方に書く。両方に同じ段落をコピーしない。要件は課題と受け入れ、設計は内部の守り方。

## いつ更新するか

| きっかけ | やること |
| --- | --- |
| 新しい Pxx の最初のデモ可能なスライス | `docs/` 一式を作る（P05 をテンプレにしてよい） |
| スライス追加で振る舞いが変わった | 仕様・API・テスト仕様・図表の該当節。索引のスライス番号 |
| スタック変更 | `DESIGN.md` が先。docs の設計書は追随 |
| ユーザーが「書類を書いて」 | 本ファイルの必須セットを確認し、足りないファイルだけ足す |
| 実装が書類より先に進んだ | 書類を直してからコミットしてよい。逆（書類だけ先の未実装）は「計画」と明示 |

ドキュメントだけの変更は、`instructions.md` の「ドキュメントだけ、も別コミット」に従う。

## エージェントへの手順

「Pxx の書類を書いて」または実装の区切りで docs が無いとき:

1. 本ファイルと対象 `DESIGN.md`、idea、`chat-context/`、製品コードとテストを読む
2. `docs/README.md` が無ければ必須セットを作る
3. 未実装スライスを「計画」として図に含めてよいが、受け入れ基準に入れない
4. 製品 README に「詳細は `project/portfolio-plan/<project>/docs/`」を 1 行足してよい（任意）

「Pxx を実装して」の通常実装では、毎回 docs 全文を読み直さなくてよい。`docs/README.md` があるときだけ索引を見て、今触る面の仕様・API を必要に応じて開く。
