## 1. 用語

| 用語 | 意味 |
| --- | --- |
| 壁時計 | TZ を付けない「9:00」。ホスト設定の入力 |
| Instant | UTC として表せる一点。API の `starts` と `slotStart` |
| ホスト現地の暦日 | その Instant を `hostTimeZone` で見た日付。例外日・book 再計算の単位 |
| オファー中 | ルール・例外・既存予約・バッファ・min notice・range を満たし、今予約してよい開始 Instant |
| 冪等キー | ゲスト（またはクライアント）が付ける再試行用キー。event type 内で一意 |

## 2. 時刻の外部契約（必須）

これが仕様の中心。要件 FR-04 / FR-05 の外部向け定義。

1. **空きの定義はホストの壁時計。** 「月曜 9:00–12:00 Asia/Tokyo」は、東京のカレンダー上のその時間だけが候補になる。
2. **API に出す開始時刻は Instant。** 例: 東京 2026-03-02 09:00 → `2026-03-02T00:00:00Z`。オフセット付き現地文字列を正にしない。
3. **ゲスト TZ は表示と記録用。** `GET slots` の `starts` 配列は `guestTimeZone` を変えても同じ。クライアントが Instant を壁時計ラベルに変換する（画面はスライス 4）。
4. **`now` はサーバー。** 最短予約期限は API プロセスの時計。クエリ `now` はテスト用。本番 UI は付けない。
5. **クライアントの `slotStart` は「どの枠を指すか」の ID。** 形式が ISO でも、オファー中でなければ予約は成立しない。
6. **range は Instant の半開区間** `[rangeStart, rangeEnd)` 相当（終了 Instant を含まない列挙窓）。14×24 時間を超えると 400。暦日 14 日ではない（DST で 14 日の長さが変わるため）。

idea 11 の初期案 `GET .../slots?date=&tz=` は採用しない。TZ をクエリで渡すと「誰の日付か」が曖昧になる。現行は Instant 窓 + レスポンスの `hostTimeZone`。

## 3. ホスト（認証あり）

現状の認証: ヘッダ `X-Dev-Host-Sub` がホストの論理 ID。無い・開発モードオフは 401。ホスト A の ID でホスト B のイベントタイプを読むと 404（存在を漏らさない）。

| 操作 | 仕様 |
| --- | --- |
| イベントタイプ作成 | slug（ケバブ、グローバル一意）、名前、所要分、バッファ、min notice、ホスト TZ、ルール配列。成功 201 |
| 一覧・取得 | 自分のホストに紐づくものだけ |
| ルール全置換 | 曜日 1=月 … 7=日、`startLocal` < `endLocal`（同日内）。日またぎ窓はエラー |
| 例外日全置換 | `YYYY-MM-DD` はホスト現地の暦日。`blocked: true` ならその日は枠ゼロ |
| ホスト向け枠一覧 | 公開と同じ計算。認証あり。PII は枠レスポンスに出さない |
| 予約一覧 | 確定予約のゲスト氏名・メールをホストだけが見る |

slug 重複は他ホストと衝突しても 409。公開 URL の一意性が目的。

## 4. ゲスト（認証なし）

公開 URL の slug は誰でも叩ける。レート制限は未実装（既知の制限）。

### 4.1 枠一覧

- 入力: slug、`rangeStart`、`rangeEnd`（必須、Instant）
- 出力: slug、名前、所要分、`hostTimeZone`、`starts[]`（Instant）
- 出さない: 他ゲストの名前・メール、キャンセルトークン、内部ホスト id
- 例外日・既存予約・バッファ・min notice を満たさない開始は `starts` に無い
- 存在しない slug は 404

### 4.2 予約

- 入力: `slotStart`（Instant）、氏名、メール、`guestTimeZone`、`idempotencyKey`（8–128 文字）
- メールは前後空白を除き小文字化して保存。応答で「登録済みか」は分けない
- `guestTimeZone` は IANA として解釈できなければ 400。枠計算には使わない
- オファー中なら 201。本文に予約 id、start/end Instant、ゲスト TZ、**初回のみ** `cancelToken`
- オファー外・既に埋まった枠は 409 `slot_unavailable`。本文に他ゲストのメールを出さない
- 同じ event type + 同じ冪等キー:
  - 同じ slot と同じメール → 200。予約は増やさない。`cancelToken` は再発行しない（初回の平文は再送できない）
  - 中身が違う → 409 `conflict`（キーの使い回し）
- キャンセル API は未実装。トークンを持っていても現状取り消せない（既知）

### 4.3 同時予約

2 ゲストが同じ `slotStart` を同時に POST した場合、外部から見える結果は **201 が 1 件と 409 が 1 件**。確定予約は 1 件。どちらが 201 かは規定しない。

## 5. スロット生成（外部から見た規則）

所要時間刻みで、ルール窓に収まる開始だけが候補。例: 9:00–12:00・30 分なら 9:00, 9:30, …, 11:30。12:00 開始は窓の終了を超えるので出ない。

バッファ N 分は、既存予約の前後 N 分に少しでも重なる候補を落とす。min notice は `now + minNoticeMinutes` より前の開始を落とす。

DST: ホスト TZ で存在しない壁時計は枠にしない。秋の重複時間は Instant として一意（同じ壁時計が 2 回あっても開始 Instant は別）。詳細の期待値はテスト仕様 TS-E。

## 6. エラー（呼び出し側契約）

| HTTP | code | いつ |
| --- | --- | --- |
| 400 | `invalid_request` | バリデーション、不正 TZ、range 逆転、14 日超 |
| 401 | `unauthorized` | ホスト API でヘッダ不足または dev auth オフ |
| 404 | `not_found` | slug / id が無い、または他人のリソース |
| 409 | `slot_unavailable` | オファー外または重なり |
| 409 | `conflict` | slug 重複、冪等キーの中身不一致 |
| 503 | （ready） | store ping 失敗 |
