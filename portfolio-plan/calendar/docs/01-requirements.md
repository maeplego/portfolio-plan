## 1. 背景と目的

メールで「来週どうですか」を往復すると、空きの正本が誰のカレンダーか分からなくなる。ホストは自分の現地時間で空きを決めたい。ゲストは自分の現地時間で「いつ起きるか」を知りたい。システムは世界のどこから見ても**同じ瞬間**を指し、同じ枠を二人に渡してはならない。

P05 はそれを共有サービスにする。Calendly の学習用ミニ実装。P10 の面接調整、将来の P04 ミーティングの裏側になる。学習用であり、本番 Calendly の置き換えではない。

P09 勤怠とは統合しない。勤怠は労務・締日・法定時間、予約は公開スロットであり、アクターも一貫性境界も違う。

## 2. スコープ

### 含む（スライス 1–3 で満たす）

- ホストがイベントタイプ（所要時間、バッファ、最短予約期限、ホスト TZ、曜日ごとの壁時計ルール、例外日）を持てる
- システムがホスト現地のルールから空き枠（Instant）を計算する
- ゲストが公開 slug で枠一覧を取り、予約できる（ログイン不要）
- 同じ枠の確定予約は 1 件だけ（同時リクエストを含む）
- ゲスト TZ は記録する。枠の集合はゲスト TZ で変えない
- 公開枠一覧に他ゲストの氏名・メールを出さない

### 含まない（意図的。計画スライスでも「できた」扱いにしない）

| 項目 | 理由 |
| --- | --- |
| 公開 Web UI / ホストダッシュボード | スライス 4 |
| ホストの本番 OIDC | スライス 4。暫定は開発用ヘッダ |
| キャンセル API・ICS・リマインド | スライス 5–6。トークン発行だけ 3 で行う |
| Google カレンダー同期 | 副作用。失敗しても予約は残す前提だが未実装 |
| チームのラウンドロビン、決済、Zoom | 非目標 |
| 日をまたぐ空き窓（22:00–02:00） | slot-engine が拒否。複雑さに見合わない |
| ゲストの IdP ログイン | メール + 後続のトークンで足りる |
| 勤怠打刻 | P09 |

## 3. アクター

| アクター | 定義 | 認証（現状） |
| --- | --- | --- |
| ホスト | 空きを公開し予約を受ける人 | 開発中は `X-Dev-Host-Sub`。計画は P01 OIDC |
| ゲスト | 公開ページ相当の API から予約する人 | なし。メールは連絡先でありログインではない |
| システム（API） | 枠計算と予約確定の正 | — |
| P10（将来） | 求人ごとの面談枠をホスト代わりに使う | 内部 API 未実装。今は対象外 |

## 4. 前提・制約

- ホストのタイムゾーンは IANA 名（例: `Asia/Tokyo`）。サーバー OS のローカル TZ に依存しない
- DB に残す時刻は UTC の瞬間（`timestamptz`）
- スロット計算期間は最大 14×24 時間（Instant）。CPU 保護
- 一人開発。API と計算ライブラリは同じ TypeScript リポジトリ
- 単体デモは Compose。他 Pxx 無しで API が動く

## 5. 機能要件

識別子は仕様・テストから参照する。

| ID | 要件 | なぜ |
| --- | --- | --- |
| FR-01 | ホストはイベントタイプを作成し、自分のものだけ読める | 他人の空きルールを改ざん・閲覧させない |
| FR-02 | 空きは「ホスト TZ + 曜日 + 壁時計の開始/終了」で定義する | ホストは自分の生活リズムで考える。UTC 時刻を手で書かせない |
| FR-03 | 例外日（ホスト現地の暦日）でその日の枠を出せなくできる | 祝日・休暇 |
| FR-04 | 空き枠の列挙と予約可否はサーバーが計算する。クライアントが作った ISO を「空いている証明」にしない | 改ざん、TZ バグ、古いキャッシュ |
| FR-05 | 枠の識別子は UTC Instant。表示用のゲスト TZ は計算に使わない | ゲスト TZ 切替でホストの空きが変わると信頼できない |
| FR-06 | 既存確定予約とバッファ、最短予約期限（サーバーの now）を満たさない枠は出さない | 連続面談の移動時間、直前予約の防止 |
| FR-07 | ゲストは slug で枠一覧を取れ、オファー中の Instant だけ予約できる | 公開 UX。ログイン障壁を予約確定前に置かない |
| FR-08 | 同じ event type の確定予約は時間帯が重ならない | ダブルブッキングは製品として無意味 |
| FR-09 | 同時に同じ枠へ来た 2 リクエストは 1 件だけ成功する | 2 タブ・2 ゲストが要件の中心デモ |
| FR-10 | 同一冪等キー・同一内容の再送は追加予約しない | ネットワーク再試行で二重予約しない |
| FR-11 | 予約成功時にキャンセルトークン平文を一度だけ返す。保存はハッシュ | 後続キャンセル。ログや一覧に平文を出さない |
| FR-12 | 公開枠レスポンスにゲスト PII を含めない | 他の予約者メールの漏洩 |

## 6. 非機能要件

| ID | 要件 | なぜ |
| --- | --- | --- |
| NFR-01 | Asia/Tokyo と America/Los_Angeles、DST の抜け・重複時間をテストする | 時刻バグは目視で見つかりにくい |
| NFR-02 | 枠生成の range 上限を超えたら計算せず 4xx | 無限ループ・CPU |
| NFR-03 | 予約確定の正は `apps/api`。Next.js に book を置かない | P10 とワーカーが同じ契約を叩く |
| NFR-04 | アプリの空き判定だけで競合を終わらせない。永続化層に重なり禁止がある | TOCTOU（内部設計書） |
| NFR-05 | メール列挙（このメールは登録済み）を予約 API で漏らさない | 公開エンドポイント |
| NFR-06 | 学習用である旨を README に書く | 本番誤用 |

## 7. 受け入れ（スライス 1–3）

次を自動化または手動で示せたら、この要件定義の対象範囲は満たす。

1. 東京ホスト・平日 9:00–12:00・30 分で、月曜の枠が東京 9:00 起算の Instant 列になる
2. 同じ Instant 列を LA の壁時計に直しても、ホスト現地の空きと矛盾しない（枠の集合がゲスト TZ で増減しない）
3. 存在しない LA 春進みの 2:00 相当を枠に出さない
4. 公開 GET slots にメールや氏名が無い
5. オファー外の Instant（例: 8:00）の POST book が 409
6. 同時 2 件の book が 201 と 409 に分かれ、確定は 1 件
7. 同じ冪等キーの再送が 200 で、キャンセルトークンを再発行しない

スライス 4 の画面操作はこの受け入れに含めない。
