## 対応アイデア

## 目的

日本の業務システムで頻出する、打刻・申請・承認・月次締め・工数按分を **1 つのモジュールモノリス** で正確に実装する。P05 と統合しない。予約の空き枠と労務の労働時間は別物。

ポートフォリオ全体が Go/TS 寄りなので、ここだけ **Java / Spring Boot** にし、受託・SIer・業務寄りの選考用の別カードにする。

## リポジトリ構成（モノレポ）

画面、ドメイン、バッチが同じ「月次」という一貫性境界を共有する。ポリレポにすると締め処理と画面の DTO がすぐずれる。

```
pf-attendance/
  apps/web          # Next.js
  apps/api          # Spring Boot
  apps/batch        # 日次集計・リマインド。同じコードベースのモジュールでも可
  deploy/
```

フロントとバックで言語が違っても、製品としては 1 リポジトリが扱いやすい。OpenAPI を api が出し web が生成する。

## 勤怠期間・締め日（意図）

### いまの実装

- 期間キーは **暦月 `YYYY-MM`**（1 日〜末日）
- `POST /v1/months/{month}/close` でその暦月をロック。CSV も同キー
- 「いつ締め操作してよいか」のカレンダー日は持たない（上長が任意のタイミングで close 可）

### 実務ではよく分かれる二つ

| 概念 | 意味 | 例 |
| --- | --- | --- |
| **集計期間（period）** | どの日付の打刻を 1 まとめにするか | 毎月 21 日〜翌 20 日／暦月 1〜末日 |
| **締め操作日（close deadline）** | いつまでにロック・CSV を出すか | 給与のため **25 日に締める**、または月末より前に締める |

「月末にしかしない」想定ではないが、**期間そのものは暦月固定**なので、20 日締めの会社には足りない。月末より前に close すること自体は **今でも操作としては可能**（8 月分を 8/25 に close できる）。足りないのは **期間の切れ目を設定できること**。

### 目指す対応（段階）

| 段階 | 内容 |
| --- | --- |
| **P0（現状）** | 暦月 period。早期 close は運用で可 |
| **P1（推奨・近）** | org 設定 `periodAnchorDay`（例: 1=暦月、21=21日起算）。期間 ID と CSV／締めキーをそれに合わせる。既定は 1 で後方互換 | **完了**（2026-08-21） |
| **P2（任意）** | `closeByDay`（例: 毎月 25 日）。それ以降の日は **見込み（provisional）** 入力可。実打刻が優先 | **完了**（2026-08-21） |

## 実装順序

1. ✅ 従業員マスタ、打刻、日次労働時間（休憩控除）のテスト — `../pf-attendance` 2026-08-19。Asia/Tokyo、整数分、Compose。夜勤なし
2. ✅ 月次カレンダー UI — `GET /v1/me/month-summary` + `/calendar`
3. ✅ 修正・休暇申請と承認
4. ✅ 工数按分（合計 ≤ 勤務）
5. ✅ 月次締めと CSV
6. ✅ 未打刻リマインド（一覧。メール送信はしない）
7. ✅ P01 接続（Compose 既定は `X-Dev-User-Sub`。OIDC は `ATTENDANCE_OIDC_*` + web BFF `/api/attendance`）

## 実装上の注意点

- 日境界は Asia/Tokyo。夜勤をやるなら「勤務日」フィールドを明示。中途半端に夜勤を入れるな。MVP は日勤のみでもよい
- 代理打刻は理由必須 + 監査ログ
- 金額は出さない（給与計算しない）。出すと責任範囲が爆発する
- 36 協定アラートは閾値設定のデモに留め、法解釈しない

## 組織テナント（IdP org）

- OIDC 時は `org` scope 必須。会社＝`org_id`（テナント）
- `employees` / `closed_months` に `org_id`。打刻・申請等は従業員経由で org 境界
- Web OrgSwitcher + API の userinfo/`X-Dev-User-Org`。dev-auth 省略時はシード org
- Compose に `ATTENDANCE_OIDC_*` / web `OIDC_*` を載せる（既定は dev-auth）

## 客先常駐・SES・他社メンバー（意図）

現場に **別会社の社員** が混ざるのは普通（SES／準委任／派遣に近い配置）。勤怠の「正本」が **雇用主** と **就業先** で分かれる点を製品が無視しない。

### 社会でよくある流れ（ざっくり）

```text
雇用主（SES 会社など）          就業先（客先）
  ・給与・社保の雇用関係           ・入場・セキュリティ・案件の指揮に近い実務
  ・自社勤怠／給与の正本になりがち   ・現場の入退館・作業日報・検収用の時間
        ↑ CSV・日報・ポータルなどで渡す／二重入力することも多い
```

- **誰のシステムで打つか** は契約次第（客先のみ／自社のみ／両方）
- 客先の上長が「現場の時間」を確認し、**SES 側の上長／管理職が自社勤怠として締め・給与へ**、という二段が典型
- 同じチームに客先社員と SES が混在しても、**給与計算の雇用関係は会社ごと**（同じ画面に並んでもテナントは分けたい）

### いまの P09

- テナントは **雇用主 org ひとつ** が前提（`org_id`）
- 「客先の勤怠システム → 自社へ渡す」の **二社間連携は未実装**
- 工数のプロジェクト名で客先を表す程度は可能だが、**他社テナントへの公式連携ではない**

### 目指す対応（段階。労基・派遣法の準拠は名乗らない）

| 段階 | 内容 | 狙い |
| --- | --- | --- |
| **A（近）** | 従業員に `engagement`（雇用／客先常駐など）と `worksite`（客先名・案件コード）を持たせる。締め CSV に含める | **完了**（2026-08-21） |
| **B（中）** | `TimesheetHandoffPort`：就業側で承認した分を雇用主 org へ取り込む（モック／CSV）。二重マスタを明示 | **完了**（2026-08-21） |
| **C（後）** | 就業先 org と雇用主 org の **招待・読み取り境界**（他社メンバーが同じ案件ボードに見えるが給与データは雇用主のみ） | **完了**（2026-08-21） |

**販売上の本線**: まず **雇用主（SES／受託会社）が P09 を使う**。客先は手渡し CSV または B の取り込み。客先も同じ製品を使う構成は C。

**やらない（当面）**: 派遣法・指揮命令の法解釈エンジン、客先と雇用主の給与を同一テナントで混ぜること、P16 が客先の税計算まで面倒を見ること。

## 他プロジェクトとの契約
