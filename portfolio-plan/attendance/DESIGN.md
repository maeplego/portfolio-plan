# P09 attendance — 設計方針

## この資料の使い方

実装チャットでは次を渡す。

- `portfolio-plan/00-overview.md`
- 本ファイル
- `portfolio-idea/03-attendance-time-tracking.md`

認証結合時は `identity-platform/DESIGN.md`。

## 対応アイデア

- 03 勤怠・工数管理ツール

## 目的

日本の業務システムで頻出する、打刻・申請・承認・月次締め・工数按分を **1 つのモジュールモノリス** で正確に実装する。P05 と統合しない。予約の空き枠と労務の労働時間は別物。

ポートフォリオ全体が Go/TS 寄りなので、ここだけ **Java / Spring Boot** にし、受託・SIer・業務寄りの選考用の別カードにする。

## リポジトリ構成（モノレポ）

画面、ドメイン、バッチが同じ「月次」という一貫性境界を共有する。ポリレポにすると締め処理と画面の DTO がすぐずれる。

```
pf-attendance/
  apps/web          # Next.js
  apps/api          # Spring Boot
  apps/batch        # 日次集計・リマインド。同じコードベースのモジュールでも可
  deploy/
```

フロントとバックで言語が違っても、製品としては 1 リポジトリが扱いやすい。OpenAPI を api が出し web が生成する。

## 技術スタック

| 層 | 採用 |
| --- | --- |
| API | Java 21, Spring Boot, Spring Security, JPA または jOOQ |
| Web | Next.js, TypeScript |
| DB | PostgreSQL |
| バッチ | Spring Batch または Scheduler |
| 認証 | P01 を Resource Server として JWT/opaque 検証。開発時は test ユーザー |
| テスト | 日付境界の JUnit を厚く。Testcontainers |

## 設計思想

- **打刻はイベント。** 行を上書きして「なかったこと」にしない。修正は申請経由の補正イベント
- **サーバー時刻が正。** クライアント時計を信じない
- **締め後は変更禁止をサーバーで強制**
- **労基法の完全準拠を名乗らない。** 簡易モデルと拡張点を正直に書く
- **上長と本人と管理者で見える範囲が違う**

## 実装順序

1. ✅ 従業員マスタ、打刻、日次労働時間（休憩控除）のテスト — `../pf-attendance` 2026-08-19。Asia/Tokyo、整数分、Compose。夜勤なし
2. ✅ 月次カレンダー UI — `GET /v1/me/month-summary` + `/calendar`
3. ✅ 修正・休暇申請と承認
4. ✅ 工数按分（合計 ≤ 勤務）
5. ✅ 月次締めと CSV
6. ✅ 未打刻リマインド（一覧。メール送信はしない）
7. ✅ P01 接続（Compose 既定は `X-Dev-User-Sub`。OIDC は `ATTENDANCE_OIDC_*` + web BFF `/api/attendance`）

## 実装上の注意点

- 日境界は Asia/Tokyo。夜勤をやるなら「勤務日」フィールドを明示。中途半端に夜勤を入れるな。MVP は日勤のみでもよい
- 代理打刻は理由必須 + 監査ログ
- 金額は出さない（給与計算しない）。出すと責任範囲が爆発する
- 36 協定アラートは閾値設定のデモに留め、法解釈しない

## 他プロジェクトとの契約

P01 の `sub` と従業員 ID の紐付け。P13 が工数を分析したくなっても、P09 から PII を出さない集計エクスポートだけ許可。

P05 との連携（1on1 の時間を勤怠に入れる等）は非目標。
