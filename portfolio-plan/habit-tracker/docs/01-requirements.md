## 1. 背景と目的

毎日の小さな習慣を「今日できたか」で支え、続けている実感（ストリーク）を暦日で正しく出す。Web ばかりのポートフォリオとの差別化として、通知とローカル DB を eventual に見せるが、**スライス 1 はオフライン記録と日付境界**に絞る。

学習用であり、本番習慣アプリの置き換えではない。実在人物のログは使わない。

## 2. スコープ

### 含む（スライス 1 で満たす）

- 習慣の CRUD（頻度: 毎日 / 週 n 回）
- 当日のチェックと取り消し（SQLite）
- ストリークと月次カレンダー（純関数 + TZ / 年末テスト）
- 架空 5 習慣 × 30 日シード
- 任意の薄い同期 API（Compose）。他ユーザーの習慣が取れないこと
- モバイルアプリは Kubernetes に載せない

### 含まない（意図的）

| 項目 | 理由 |
| --- | --- |
| ローカル通知 | DESIGN 実装順 3 |
| 統計画面の作り込み | 実装順 4 |
| モバイル → API 同期クライアント | 実装順 5 |
| P01 public+PKCE | 実装順 6 |
| Watch、ソーシャルランキング、ヘルスケア | 非目標 |
| P14 との統合 | DESIGN |

## 3. アクター

| アクター | 定義 | 認証（現状） |
| --- | --- | --- |
| 個人ユーザー（端末） | 端末 SQLite の習慣だけを見る | なし（ローカル） |
| API ユーザー | 自分の習慣だけ | `X-Dev-User-Sub` |
| デモユーザー `demo` | 架空シード | 同上 |

## 4. 前提・制約

- 「今日」はユーザー TZ の暦日
- オフラインファースト。API ダウンでも記録できる
- 同期 API の `local_date` はクライアントが決めた YYYY-MM-DD。サーバは TZ 変換しない
- ID はモバイル UUID / API ULID。DB 時刻は timestamptz

## 5. 機能要件

| ID | 要件 | なぜ |
| --- | --- | --- |
| FR-01 | 今日のチェックが主操作 | DESIGN |
| FR-02 | 毎日ストリークは飛ばした日で切れる。今日未チェックだけでは切れない | 日付境界 |
| FR-03 | 週 n 回は ISO 週（月曜始まり）でクォータ | アイデア 22 |
| FR-04 | UTC 日付を今日にしない | TZ 誤用防止 |
| FR-05 | API は所有者以外 404 | 隔離 |
| FR-06 | シードは架空 | プライバシー |

## 6. 非機能

- 純関数テストは DB なし
- 単体 Compose で API が上がる
- ストア提出は必須ではない

## 7. 受け入れ（スライス 1）

- Expo で今日のチェックが SQLite に残る
- `npm test`（domain）が TZ・年末ケースで緑
- API `npm test` が隔離で緑
- Compose で `/health` `/ready` と `demo` の 5 習慣
