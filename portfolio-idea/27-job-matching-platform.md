# 求人マッチング基盤（検索・フィルタ・応募）

検索、フィルタ、ページング、保存した検索条件、応募フローを持つ求人ボードです。日本の IT 就職活動そのものがドメインなので、物語が作りやすく、Elasticsearch 相当の検索設計を見せられます。

## 概要

企業側の求人投稿と、候補者の検索・応募・メッセージ（簡易）を提供します。Indeed / Green のミニ版。レコメンド（20 番）を後から足すこともできます。

## 就職活動でのアピールポイント

- 検索 UX（キーワード、勤務地、年収、リモート、スキルタグ）
- インデックス設計、日本語形態素（Kuromoji 等）
- 複合フィルタとファセット（件数）
- 応募の状態機械
- 多ロール（候補者 / 企業 / 管理者）

## 解決する課題

求人サイトの一覧が雑で、条件を保存して新着を追えない問題。ポートフォリオとしては「検索が速い・意図した順」が価値です。

## 想定ユーザー

IT エンジニア候補者と採用担当。デモデータは架空企業 50 社、求人 200 件。

## 主要機能

### 必須（MVP）

- 求人 CRUD（企業ロール）
- 検索（キーワード、雇用形態、勤務地、スキル）
- ソート（新着、年収）
- 求人詳細、応募（履歴書テキスト）
- 応募ステータス（応募済み / 書類通過 / 不合格）企業側が更新
- 候補者プロフィール（スキル、希望）

### 推奨

- 保存した検索と新着通知（バッチ）
- ファセット（この条件でのリモート件数など）
- 地図（任意、勤務地ジオコードは固定データで可）
- ブックマーク
- 企業ページ
- 管理画面（公開/非公開、通報）

### 発展

- マッチ度スコア（プロフィールと求人タグの overlap）
- メッセージスレッド（12 番の縮小）
- スクレイピングは利用規約と法律の問題があるのでやらない。データは自作シード

## 画面構成

| 画面 | 役割 |
| --- | --- |
| 検索 | メイン |
| 求人詳細 | 応募 CTA |
| マイ応募 | 候補者 |
| 応募者一覧 | 企業 |
| プロフィール | スキル編集 |

## API 概要

- `GET /jobs/search?q=&tags=&page=`
- `POST /jobs/:id/applications`
- `PATCH /applications/:id/status`
- `GET /me/saved-searches`

検索は API のクエリパラメータ設計がそのまま評価されます。

## 技術スタック（推奨）

| 層 | 候補 |
| --- | --- |
| フロント | Next.js、TypeScript、フィルタ UI |
| API | NestJS / Rails |
| 主 DB | PostgreSQL |
| 検索 | OpenSearch / Elasticsearch、または Postgres FTS + pg_trgm で開始し、理由を書く |
| 日本語 | 解析器の設定を README に |
| インフラ | Docker（OpenSearch はメモリに注意。開発は FTS でも可） |

最初から ES 必須にするとマシンが重いので、「200 件は Postgres、1 万件超えたら OpenSearch」と段階を書くのも設計力です。

## アーキテクチャ

求人の正は Postgres。公開時に検索インデックスへ同期（トランザクション後のイベントまたは outbox）。検索 API はインデックス、詳細は Postgres（最新の本文）。

## データモデル（概要）

- `companies`, `jobs`（status, salary_min/max, location, employment_type）
- `skills`, `job_skills`, `user_skills`
- `applications`（status, resume_snapshot）
- `saved_searches`

年収は範囲検索できる数値で持つ。文字列「応相談」はフラグ。

## セキュリティ・品質

- 応募者情報は企業の担当以外読めない
- 履歴書のスナップショット（求人変更後も当時の内容）
- 個人情報の削除（候補者アカウント削除）
- 公開デモでは実在人物のデータを使わない

## 実装の進め方

1. 求人と応募の CRUD
2. フィルタ検索
3. インデックスとファセット
4. 保存検索と通知
5. シードの質（リアルな職種名）
