# SRE ランブックポータル＋障害対応シミュレーター

障害対応の手順書（ランブック）を実行可能なチェックリストにし、ゲーム的なインシデントシミュレーションで「観測 → 仮説 → 対応」を練習します。04 番・18 番と並ぶ SRE 志望の仕上げに適した題材です。ドキュメントとシステムの中間に位置します。

## 概要

サービスごとのランブック（症状、確認コマンド、判断分岐、エスカレーション先）を管理し、訓練モードでは架空の障害シナリオを進めてスコアを出します。実システムを壊す必要はなく、状態はシミュレータ内の仮想メトリクスで十分です。

## 就職活動でのアピールポイント

- 運用設計（SLO、症状ベースの手順）
- 状態機械としてのシナリオ
- 技術文書の構造化（単なる Wiki より実行可能）
- 教育・オンボーディングへの関心
- 既存の 04 / 18 と連携すると物語が一本になる

## 解決する課題

障害時に Wiki が古く、手順が人の頭にしかない問題。新人は本番を壊せずに手順を学べない問題。

## 想定ユーザー

オンコールに入り始めたエンジニア。デモは「チェックアウト 5xx が急増」シナリオ。

## 主要機能

### 必須（MVP）

- サービスとランブック CRUD（Markdown + チェックリスト）
- 手順ステップの順序、確認項目、戻る/分岐（「DB CPU 高いか？」Yes/No）
- 訓練シナリオ: 仮想ダッシュボード（エラー率、レイテンシ、デプロイ有無）
- ユーザーの選択に応じて状態が変化し、正解経路で復旧
- 結果（時間、誤った操作数、使ったヒント）

### 推奨

- 複数シナリオ（デプロイ不良、依存 API 遅延、ディスク満杯、誤った設定フラグ）
- ヒントと「 spoil せずに次の観測を促す」メッセージ
- ランブックとシナリオのリンク（訓練後に本番手順へ）
- チームの訓練履歴（誰がいつクリアしたか）
- 外部コマンドは実行せず、シミュレータ上の「仮想 kubectl / SQL」出力を見せる（安全）

### 発展

- 本番メトリクスを読むモードは権限と誤操作リスクがあるので、ポートフォリオではオフ、または読み取り専用のデモ環境に限定
- 04 番のインシデント作成、18 番の Grafana 埋め込み
- ポストモーテムテンプレ生成

実クラスタに対して破壊的コマンドを送る機能は実装しないでください。学習用は必ずシミュレーションに閉じます。

## 画面構成

| 画面 | 役割 |
| --- | --- |
| サービス一覧 | ランブック入口 |
| ランブック | チェックリスト |
| 訓練 | 左右分割（観測パネル / 手順） |
| 結果 | 振り返り |
| 編集 | シナリオ YAML |

## API 概要

- `GET/PUT /services/:id/runbooks`
- `POST /drills/:scenarioId/start`
- `POST /drills/:sessionId/actions`（observe, mitigate, rollback, escalate）
- `GET /drills/:sessionId`（現在の仮想メトリクス）

## 技術スタック（推奨）

| 層 | 候補 |
| --- | --- |
| フロント | Next.js、チェックリスト UI、小さなチャート |
| バックエンド | NestJS / Rails |
| シナリオ定義 | YAML（状態、遷移、成功条件）をコード化するとレビューしやすい |
| DB | PostgreSQL（ランブック、セッション） |
| テスト | シナリオ遷移の単体テストが本領 |
| インフラ | Docker、GitHub Actions |

## アーキテクチャ

シナリオエンジンが有限状態機械。アクションは許可リスト。観測は状態から合成した時系列を返す。ランブック本文は Markdown で、訓練の「推奨ステップ ID」と相互リンク。

## データモデル（概要）

- `services`, `runbooks`, `runbook_revisions`
- `scenarios`（yaml）
- `drill_sessions`（user_id, state, started_at, score）
- `drill_events`（action, at）

## シナリオ例（概要）

1. 症状: チェックアウト 5xx 20%
2. 観測: 直近デプロイが 10 分前、在庫サービス p99 が 2s
3. 誤った操作: アプリをスケールアウト → 改善しない
4. 正しい操作: 在庫サービスの不良デプロイをロールバック → 5xx 低下
5. 終了条件: エラー率 < 1% かつ チェックリスト完了

## セキュリティ・品質

- 任意コード実行をランブックに埋め込まない
- 本番資格情報をシナリオに書かない
- 公開デモは訓練のみ、編集は管理者

## 実装の進め方

1. ランブック Wiki（02 番より手順特化）
2. 1 シナリオの状態機械
3. 観測パネル
4. 採点と履歴
5. シナリオを 3 本に増やす（質が量より重要）

## 工数目安

- MVP: 2〜3 週間
- 推奨: 4 週間（シナリオの文章品質含む）

## 面接での話し方

「障害対応はツールより意思決定」と位置づけ、なぜロールバックを先に検討するか、をシナリオで示せます。SRE 本の知識を、動く教材にした点が差別化です。破壊的な自動修復を自慢しないこと。
