# ログ・メトリクス監視基盤（ミニ可観測性スタック）

アプリに計装し、ログ・メトリクス・トレースを集め、ダッシュボードとアラートまで通します。SRE 志望の定番で、「ツールを docker compose しただけ」にしないために、計装設計と SLO を自分の言葉で書きます。

## 概要

サンプルアプリ（決済風 API）に OpenTelemetry を入れ、Grafana で RED メトリクス（Rate, Errors, Duration）、ログ検索、トレースを見ます。SLO（例: 月間可用性 99.5%）とエラーバジェットの説明を README に含めます。

## 就職活動でのアピールポイント

- 計装（トレース ID の伝播）
- メトリクス設計（カーディナリティ爆発を避ける）
- ログの構造化、相関
- アラートの品質（症状ベース）
- ランブックへのリンク

## 解決する課題

障害時に「どのエンドポイントが遅いか」「DB か外部 API か」が分からない状態を解消します。

## 想定ユーザー

自分の API を運用する開発者。デモは意図的に遅延とエラーを注入できる管理エンドポイント。

## 主要機能

### 必須（MVP）

- 構造化ログ（JSON、request_id）
- Prometheus メトリクス（http_requests_total, latency histogram）
- Grafana ダッシュボード 1 枚
- トレース（OTel Collector → Jaeger または Tempo）
- エラー注入 API（開発時のみ）

### 推奨

- ログ基盤（Loki）でトレース ID 検索
- アラート（5xx 比率、p99 遅延）→ Discord / Slack / メール
- SLO ダッシュボード（残りエラーバジェット）
- 依存関係マップ（サービスグラフ）
- サンプルアプリは DB と外部 HTTP 呼び出しを含む

### 発展

- プロファイリング（Pyroscope）は任意
- 04 番インシデント管理へアラートを飛ばす連携は非常に強い

## 画面構成

Grafana が UI の中心です。サンプルアプリの「ショップ」画面は最小。README に「見る場所」のスクショを固定します。

## 計装設計

- トレース: 入口で span、DB は instrumentation
- メトリクスラベル: `path` はパラメータを正規化（`/users/:id`）。生 ID をラベルにしない
- ログ: トレース ID を同じキー名で入れる

## 技術スタック（推奨）

| 層 | 候補 |
| --- | --- |
| アプリ | Go または Node（OTel 公式が厚い） |
| コレクタ | OpenTelemetry Collector |
| メトリクス | Prometheus |
| トレース | Jaeger または Grafana Tempo |
| ログ | Grafana Loki |
| 可視化 | Grafana |
| 起動 | Docker Compose プロファイル |

## アーキテクチャ

App → OTel SDK → Collector → Prometheus/Loki/Tempo。Grafana がそれぞれをデータソースにします。アプリは直接 Jaeger に送らず Collector 経由にすると、後で変更しやすいと説明できます。

## データ（保持）

学習用なので保持 24h〜数日。ディスク使用量を README に書く。

## セキュリティ・品質

- Grafana を 0.0.0.0 で公開しない、または強力なパスワード
- PII をログに出さない（注入デモでも）
- エラー注入エンドポイントは本番ビルドで無効化

## 実装の進め方

1. アプリ + Prometheus + Grafana
2. 構造化ログ + Loki
3. トレース
4. アラートと SLO
5. 障害注入シナリオを 3 つ文書化

## 工数目安

- MVP: 1〜2 週間
- 推奨: 3 週間

## 面接での話し方

「アラートは CPU 80% ではなく、ユーザーのエラー率にした」が良い答えです。カーディナリティで Prometheus が死ぬ話を知っていると差が付きます。
