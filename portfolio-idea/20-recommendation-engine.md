# レコメンドエンジン（協調フィルタリング＋評価 API）

機械学習を「ノートブックで完結」させず、学習ジョブ・モデル保存・オンライン推論 API・オフライン評価まで製品として見せます。ML エンジニア、データサイエンティスト、MLOps 志望向けです。

## 概要

架空の EC または映画の評価データ（MovieLens など公開セット）で「このユーザーへのおすすめ」を返します。人気ベース、アイテム類似、行列因子分解（または単純な近傍法）を比較し、メトリクス（Recall@K, NDCG）を報告します。

## 就職活動でのアピールポイント

- 問題設定（暗黙的フィードバック vs 評価値）
- オフライン評価とデータリーク防止
- バッチ学習と低レイテンシ推論の分離
- コールドスタート
- 実験管理（パラメータ、データバージョン）

## 解決する課題

新着一覧だけだと発見性が低い。行動履歴から次に見そうなアイテムを提示します。

## 想定ユーザー

小さなメディア / EC。デモ UI は「ユーザーを選ぶと 10 件出る」。

## 主要機能

### 必須（MVP）

- データ取り込み（評価 or 閲覧ログ）
- 学習ジョブ（定期または手動）
- `GET /recommend?userId=&k=10`
- 人気商品フォールバック（履歴が少ないユーザー）
- オフライン評価レポート（Markdown または MLflow）

### 推奨

- アイテムページの「類似アイテム」
- 多様性（同じカテゴリばかりを少し抑制）
- フィードバック API（表示、クリック）をログし、再学習の材料にする
- 特徴量の説明（なぜ勧めたか、類似アイテム名）
- キャッシュ（ユーザーごとの結果を Redis）

### 発展

- ディープラーニングはデータと説明コストが大きい。必要なら Two-Tower 程度
- オンライン A/B はトラフィックが無いので、オフライン比較＋シミュレーションに留める

## 画面構成

| 画面 | 役割 |
| --- | --- |
| デモ | ユーザー選択、推薦リスト、クリック |
| 実験 | モデル比較表 |
| アイテム | 類似 |

## API 概要

- `GET /recommend`
- `GET /similar-items/:id`
- `POST /events`（view, click）
- `POST /admin/train`（保護）

## 技術スタック（推奨）

| 層 | 候補 |
| --- | --- |
| 学習 | Python、pandas、implicit / LightFM / surprise、scikit-learn |
| 実験 | MLflow または単純な metrics.json |
| 推論 API | FastAPI |
| 保存 | アイテムベクトルを npz / Redis、メタデータは Postgres |
| ジョブ | 定期は GitHub Actions またはワーカー |
| デモ UI | Streamlit でも、React でも可 |
| インフラ | Docker（API + 学習は別イメージでも可） |

## アーキテクチャ

オフライン: ログ → 学習 → アーティファクト（S3/MinIO）→ 推論がロード。オンライン: API は行列の内積または近傍検索。再学習中は旧モデルを使い続ける（ホットスワップは推奨）。

## データモデル（概要）

- `users`, `items`, `interactions`
- `model_registry`（version, metrics, path）
- `prediction_cache`

## セキュリティ・品質

- 学習データに実在ユーザーの個人情報を使わない
- 管理用 train エンドポイントは認証
- 評価時に未来データを使わない（時間で split）

## 実装の進め方

1. 人気ベース API（ベースライン）
2. 協調フィルタ
3. 時間ベース split で評価
4. コールドスタート
5. デモ UI とレポート

## 工数目安

- MVP: 2 週間
- 推奨: 3〜4 週間

## 面接での話し方

「精度だけ追わず、ベースラインより何が良くなったか」を表で示します。リークをどう防いだかは必ず話します。ML を使ったことより、製品への載せ方が見られます。
