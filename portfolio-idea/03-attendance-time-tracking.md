# 勤怠・工数管理ツール

日本の業務システムで需要が高い勤怠・工数管理です。日付・タイムゾーン・承認フロー・集計といった、Web アプリでは見落とされがちなドメインを扱える点が強みです。SaaS 企業や受託開発の選考で説明しやすいです。

## 概要

出退勤打刻、休暇申請、プロジェクト別工数入力、月次締めを提供します。単なる CRUD ではなく「締め後は編集不可」「承認者の代理」など業務ルールをコードに落とすことが目的です。

## 就職活動でのアピールポイント

- 複雑なドメインモデリング（勤務形態、休憩、深夜、休日）
- 承認ワークフロー
- 集計バッチ、CSV 出力、帳票
- タイムゾーンと「日付の境界」の扱い
- 監査ログ（誰がいつ打刻を修正したか）

## 解決する課題

Excel 勤怠の転記ミスと、プロジェクト原価が見えない問題を減らします。エンジニア自身が使うツールなので、UX の改善点も語れます。

## 想定ユーザー

中小企業の従業員と上長、経理。デモでは「開発部 8 名」の組織を用意します。

## 主要機能

### 必須（MVP）

- 出勤 / 退勤 / 休憩の打刻（Web、ボタン 1 つ）
- 日次の労働時間自動計算（休憩控除）
- 月次カレンダー表示、打刻修正申請
- 上長による承認 / 差戻し
- 有給・欠勤などの休暇区分
- プロジェクト・タスクへの工数按分（1 日の合計が勤務時間を超えない）

### 推奨

- フレックス、裁量労働の簡易対応（コアタイム警告）
- 36 協定を意識した残業時間アラート（閾値は設定値）
- 締め処理（月次ロック）と CSV エクスポート
- 管理者の代理打刻（理由必須、監査ログ）
-  loc 通知ではなく、未打刻リマインドメール

### 発展

- IC カードや Slack `/kintai` コマンド
- 給与ソフト向けの標準フォーマット出力
- シフト管理（小売・飲食向け）は範囲が広いので別モジュールとして切り出す

## 画面構成

| 画面 | 役割 |
| --- | --- |
| 打刻ホーム | 大きい打刻ボタンと本日サマリー |
| 月次カレンダー | 日別の出退勤、承認状態 |
| 申請一覧 | 修正・休暇の承認キュー（上長） |
| 工数入力 | 案件別の時間 |
| 管理 | ユーザー、勤務体系、締め |

## API 概要

- `POST /punches`（clock_in / clock_out / break）
- `POST /requests`（type: punch_edit, leave）
- `POST /requests/:id/approve`
- `GET /me/monthly-summary?yearMonth=2026-08`
- `POST /admin/close-month`
- `GET /exports/attendance.csv`

## 技術スタック（推奨）

| 層 | 候補 |
| --- | --- |
| フロント | Next.js、TypeScript、FullCalendar または自前グリッド |
| バックエンド | Java（Spring Boot）または C#（ASP.NET）も業務寄りのアピールになる。Node.js / Go でも可 |
| DB | PostgreSQL |
| バッチ | 日次集計は SQL またはジョブ（BullMQ / Sidekiq / Spring Batch） |
| インフラ | Docker、GitHub Actions |
| テスト | 日付境界のユニットテストを厚くする |

Java / C# を出すと、SIer・業務システム志望との相性がよくなります。Web 系志望なら TypeScript フルスタックで問題ありません。

## アーキテクチャ

打刻は追記型のイベント（`punches`）として保存し、日次サマリーは計算結果をキャッシュします。修正は punch を直接書き換えず、申請→承認後に補正イベントを足すと、監査の説明がしやすいです。

## データモデル（概要）

- `employees`, `employment_terms`（所定労働、コアタイム）
- `punches`（type, punched_at, source）
- `daily_summaries`（work_minutes, overtime_minutes, status）
- `requests`, `approvals`
- `projects`, `time_entries`
- `month_closes`

## セキュリティ・品質

- 他人の勤怠は管理者・上長以外読めない
- 締め後編集禁止をサーバー側で強制
- 打刻時刻の改ざん防止（クライアント時刻を信じずサーバー時刻を採用。オフライン打刻は発展）

## 実装の進め方

1. 打刻と日次計算（テストファーストが向く）
2. 月次画面と修正申請
3. 工数按分
4. 締めと CSV
5. デモ組織のシード

## 工数目安

- MVP: 3 週間
- 推奨: 5 週間（承認と集計を丁寧に）

## 面接での話し方

「サーバー時刻を採用した理由」「日をまたぐ夜勤をどうモデル化したか」は必ず聞かれます。完璧な労基法準拠を名乗らず、「学習用の簡易モデルで、拡張ポイントはここ」と正直に話す方が信頼されます。

## 公開時のチェックリスト

- タイムゾーンを Asia/Tokyo に固定したことを明記
- 境界値テストの一覧（23:59、0:00、休憩未終了）
- 上長アカウントと一般アカウントのデモ手順
