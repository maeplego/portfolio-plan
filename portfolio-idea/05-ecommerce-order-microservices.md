# マイクロサービス型 EC 注文システム

商品・在庫・注文・決済をサービス分割したミニ EC です。「なぜ分割したか」「同期と非同期の境界」を語れることが、モノリス CRUD との差になります。バックエンド・アーキテクチャ志望向けです。

## 概要

カタログ、カート、注文、在庫、決済（ダミー）、通知を分け、API Gateway 配下で動かします。実決済は使わず、Stripe のテストモードまたは完全モックにします。

## 就職活動でのアピールポイント

- サービス境界の設計、DB per service
- 同期 REST と非同期メッセージングの使い分け
- Saga / 補償トランザクションの基礎
- 分散トレーシング、相関 ID
- Docker Compose または Kubernetes での複数サービス起動

## 解決する課題

単一 DB の巨大 EC ではなく、注文増加に備えて在庫と注文を独立デプロイできるようにします。学習目的なので、分割しすぎない（4〜6 サービス）ことが重要です。

## 想定ユーザー

小さな D2C ブランドのオンラインストア。デモ商品は 20 点程度。

## 主要機能

### 必須（MVP）

- 商品一覧・詳細、在庫数表示
- カート、チェックアウト
- 注文作成（在庫引当 → 決済モック → 確定）
- 注文履歴、ステータス（pending / paid / shipped / cancelled）
- 在庫不足時の失敗と補償（引当解除）

### 推奨

- 管理画面（商品登録、出荷処理）
- メール通知（注文確定）
- べき等な決済リクエスト（同じ checkout を 2 回押しても二重課金しない）
- OpenAPI をサービスごとに公開
- 分散トレース（OpenTelemetry）

### 発展

- クーポン、ポイント
- 検索（OpenSearch）
- 出品者複数（マーケットプレイス化）は範囲过大なので避ける

## サービス分割案

| サービス | 責務 | データ |
| --- | --- | --- |
| gateway | 認証、ルーティング、レート制限 | なし |
| catalog | 商品マスタ | 商品 DB |
| cart | カート | Redis でも可 |
| inventory | 在庫引当・解放 | 在庫 DB |
| order | 注文ライフサイクル | 注文 DB |
| payment | 決済モック | 決済 DB |
| notify | メール | なし |

## API / イベント概要

- 同期: `POST /orders` は order がオーケストレーション、または choreography
- イベント: `OrderCreated`, `InventoryReserved`, `PaymentCompleted`, `OrderCancelled`
- メッセージブローカー: RabbitMQ または NATS、Kafka は学習コストが高いので任意

## 技術スタック（推奨）

| 層 | 候補 |
| --- | --- |
| フロント | Next.js のシンプルなストアフロント |
| 各 API | Go または NestJS（同一言語に揃えると説明が楽） |
| DB | サービスごとに PostgreSQL スキーマ、またはコンテナ分割 |
| メッセージ | RabbitMQ |
| 観測 | OpenTelemetry + Jaeger、Prometheus / Grafana |
| インフラ | Docker Compose 必須。K8s は 17 番アイデアと役割分担してもよい |

## アーキテクチャ

チェックアウト時は order サービスがプロセスマネージャとなり、inventory → payment を順に呼び、失敗時は補償イベントを出します。カタログ閲覧は同期 REST のままで十分です。

## データモデル（概要）

- catalog: `products`, `product_images`
- inventory: `stocks`, `reservations`（ttl）
- order: `orders`, `order_items`, `outbox`
- payment: `payments`（idempotency_key）

Outbox パターンを 1 サービスでも入れると、メッセージングの信頼性を語れます。

## セキュリティ・品質

- 決済は本物のカードを扱わない
- サービス間は内部ネットワーク、gateway のみ公開
- 冪等キーをチェックアウトに必須化

## 実装の進め方

1. モノリスで注文フローを先に正しく作る
2. 境界に沿ってサービス抽出
3. イベントと補償
4. トレーシングと障害注入（在庫サービスを止めるデモ）

最初から分割すると完成しないことが多いです。README に「モノリスから抽出した」と書けると評価されます。

## 工数目安

- モノリス MVP: 2 週間
- 分割まで: 合計 5〜8 週間

## 面接での話し方

「全部をマイクロサービスにする必要はない。注文と在庫が独立してスケールしたいので分けた」と言い切れることが重要です。分割のデメリット（運用負荷、一貫性）も自分の言葉で話します。

## 公開時のチェックリスト

- `docker compose up` 一発起動
- シーケンス図（成功時 / 在庫不足時 / 決済失敗時）
- Jaeger のスクショ
