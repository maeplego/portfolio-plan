# CI パイプライン可視化ダッシュボード

GitHub Actions や自前ランナーの実行履歴、失敗ログ、所要時間、フレーク検出を可視化します。DevOps 志望、プラットフォームエンジニア志望向けです。自前 CI エンジンまで作ると重いので、まずは GitHub API の観測＋簡易オーケストレーションに分割して考えます。

## 概要

リポジトリを登録すると、ワークフロー実行を取り込み、成功率、平均時間、失敗ジョブの上位をダッシュボード化します。発展として「YAML を受けてコンテナでテストを回す」ミニ CI を足せます。

## 就職活動でのアピールポイント

- GitHub API / Webhook、ページング、レート制限
- 時系列データの集計と可視化
- ログの保存とマスキング
- （発展）コンテナ隔離でのジョブ実行
- DX（開発者体験）への関心

## 解決する課題

Actions の画面を横断せず、チームの「今 CI が赤いか」「何が遅いか」を一目で見たい。

## 想定ユーザー

開発チームのテックリード。デモは自分の公開リポジトリ。

## 主要機能

### 必須（MVP）

- GitHub App または PAT でリポジトリ接続
- 実行一覧（成功/失敗、branch、actor、duration）
- ワークフロー別の成功率グラフ（14 日）
- 失敗したジョブのログ閲覧（末尾 N 行）
- Webhook によるほぼリアルタイム更新

### 推奨

- フレーク検出（同一テストが間欠失敗）
- 実行時間の回帰アラート（平均 + 2σ）
- ブランチ保護の有無などリポジトリ健全性スコア（簡易）
- Slack 通知（main が赤になったとき）
- チームのリードタイム（merge までの時間）は GitHub データから概算

### 発展（ミニ CI エンジン）

- `pipeline.yml`（checkout, run commands）
- Docker でジョブ実行、タイムアウト、成果物保存
- これはセキュリティリスクが高いので、ローカル専用・信頼できないコードを回さないと明記

## 画面構成

| 画面 | 役割 |
| --- | --- |
| オーバビュー | 赤緑、MTTR 風の平均修復（失敗から次の成功） |
| リポジトリ詳細 | 実行タイムライン |
| 実行詳細 | ジョブ、ログ |
| 設定 | Webhook、通知 |

## API 概要

- 取り込み: GitHub Webhook `workflow_run`
- `GET /repos/:id/runs`
- `GET /runs/:id/logs`（保存済み）
- 発展: `POST /pipelines/:id/trigger`

## 技術スタック（推奨）

| 層 | 候補 |
| --- | --- |
| フロント | Next.js、Recharts |
| バックエンド | Go / Node |
| DB | PostgreSQL |
| ログ保存 | S3 または DB（短いログなら） |
| インフラ | Docker、GitHub Actions（自分自身を計測するメタさは好印象） |

## アーキテクチャ

Webhook → 署名検証 → run メタデータ upsert → 非同期で logs API 取得 → マスキング → 保存。ダッシュボードは集計テーブルを 10 分ごとに更新でも可。

## データモデル（概要）

- `installations`, `repositories`
- `workflow_runs`, `jobs`
- `log_blobs`（storage_key）
- `metrics_daily`

## セキュリティ・品質

- Webhook secret
- ログからトークンらしき文字列をマスク
- PAT の最小化（Actions 読み取りのみ）
- 自前ランナーを公開インターネットに置かない

## 実装の進め方

1. 手動同期で run 一覧
2. Webhook
3. グラフと失敗ランキング
4. ログ
5. 任意でローカルミニ CI

## 工数目安

- 可視化 MVP: 2 週間
- ミニ CI まで: +3 週間（非推奨 unless インフラ志望）

## 面接での話し方

「観測と実行基盤は分けた」と言い切ると安全です。CI を自作した場合は、隔離とシークレット注入をどうしたかが必ず聞かれます。
